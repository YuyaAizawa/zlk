# ZLK Change Execution

## 概要

ZLKの承認済み設計または限定された変更単位を，既存変更を保護しながら実装し，実測したGREENまで到達させるための手順を定める．サブエージェントであるかどうかではなく，実装結果に責任を持つ役割に適用する．

このSKILLの目的は，再設計によるscope拡大，調査だけでの終了，長時間コンパイル不能な状態，検証前のtool call枯渇，不完全な引き継ぎの防止である．

## 適用条件

以下の場合に使用する．

- 承認済み設計に基づく機能追加または不具合修正
- coordination担当から委任された限定スライスの実装
- 一つのエージェントが設計を終え，実装段階へ移る場合
- 途中終了した変更について，実エラーと残作業が示された継続実装

次の場合には使用しない．

- 設計，分割，委任，統合を担当する作業。この場合は`zlk-change-coordination`を使用する
- 受け入れ基準が存在せず，設計選択から始める必要がある作業
- コード変更を伴わない単純な調査

## 役割と権限

execution担当は，提示された目標，承認済み設計，scope，non-goals，受け入れ基準を実装契約として扱う．

- タスクの再委任禁止
- 明示的な許可を伴わない`git commit`と`git rebase`の禁止
- 既存の未コミット変更の削除，上書き，巻き戻しの禁止
- scope外の広いrefactorと別不具合修正の禁止
- 実測していないGREEN，テスト結果，ファイル状態の報告禁止

設計上の矛盾または重大な不足がある場合は，独自の別設計へ無言で変更しない．コードとテストから解決できる事実は調査し，設計判断が必要な問題だけを，根拠，影響，必要な判断とともにblockerとして報告する．

## 手順

### 1．実装契約と開始状態の確認

最初に次を確認する．

- 目標と現在の動作
- 承認済み設計と決定済み事項
- 変更範囲とnon-goals
- 受け入れ基準
- 最初の実装checkpoint
- 必須テストと検証コマンド
- 保持すべき既存変更
- 実装コンテキスト目録と，追加調査に認められた裁量
- 既知の不確実性と，coordination担当が引き受ける最終検証

続いて`git status`と関連diffを確認し，既存変更と自分が追加する変更を区別する．親会話の内容を参照できると仮定せず，実装コンテキスト目録とリポジトリ内の正本から開始する．目録は読解範囲の上限ではない．詳細設計，命名，既存抽象化，呼出関係，エラー処理，テスト慣例の一貫性に必要な追加読解は行う．変更scopeと読解scopeを同一視せず，目的や仮説を持たないリポジトリ全体の網羅探索だけを避ける．

契約の欠落があっても，実装とテストから一意に回収できる情報は自分で確認する．受け入れ基準または設計が複数の意味を持ち，選択によって公開動作やIRの不変条件が変わる場合だけblockerとする．

**完了条件：** 変更対象，保持対象，GREEN条件を区別して説明できること．

### 2．最初のcheckpointへの到達

不具合修正または観測可能な機能追加では，原則として次の順序で進める．

1. 対象に最も近い既存実装，テスト，同種の抽象化を目的を持って読解
2. 失敗する回帰テストまたは受け入れテストの追加
3. 期待した理由で失敗することの確認
4. 最小のproduction変更
5. focused testのGREEN確認

テストを先に書けない基盤変更では，最小のproduction compileまたは既存focused testをcheckpointとし，長時間コンパイル不能な広い変更を作らない．新しい型やAPIへの移行は，小さい参照集合ごとにcompileを戻してから次へ進める．

REDが期待と異なる理由で発生した場合は，production実装へ進まず，テストまたは前提を修正する．既存の正しい仕様を推論上の制限と誤認しないよう，構文規則，既存テスト，実行時意味論を確認する．

**完了条件：** 変更が必要であることを示すRED，または基盤変更の最小compile checkpointを実測していること．

### 3．フェーズ境界と不変条件を保つ実装

実装中は次を確認する．

- 新しい情報の所有者となるフェーズまたは型
- その情報を後続フェーズへ渡す既存の経路
- 入力IRと出力IRの責務
- 後続フェーズが仮定できる不変条件
- 同じ概念を表す既存抽象化
- 周辺コードで使われている命名，型の分割，エラー処理，テスト記法

後段の都合を前段へ持ち込まず，構文解析後のASTを変更しない．型推論ロジックや`Type`抽象化を迂回する並行実装を作らない．既存テストを通すためだけの例外的な内部表現より，意味論に基づく一貫した生成規則を優先する．

compile成功だけでは，kind，rank，occurs，lacks，重複保持，循環などの意味論的不変条件を証明できない．今回の設計契約で重要な不変条件は，focused testまたは直接的なコード上の検査で確認する．

**完了条件：** 各変更を，所有者，受け渡し経路，不変条件のいずれかへ対応付けられること．

### 4．scopeを保った反復

一つの垂直スライスについて，次を短い周期で繰り返す．

1. 一つの失敗原因または一つの振る舞いへの変更
2. production compile
3. focused test
4. diff確認

別の不具合や改善を見つけても，受け入れ基準に不要なら実装しない．必要なら完了報告で別課題として示す．scope内の小規模な修正が残っている場合は，「あと数行」と報告して終了せず，実装と検証を完了させる．

検索，読み込み，コマンドが失敗した場合は，同じ方法を無変更で繰り返さず，パス，対象ファイル，実行環境を確認して別の方法へ切り替える．

**完了条件：** working treeがcompile可能で，focused testがGREENであること．

### 5．想定外の管理と検証責任

委任契約にcoordination担当がいる場合，execution担当は原則として次を直接検証する．

- production compile
- 変更に最も近いfocused test
- 自身の変更scopeのdiff
- 実測したGREEN，または再開可能なcompile／test error

統合後のfocused test，full test，baseを考慮したdiff check，最終statusは，委任契約でcoordination担当へ割り当てられていれば重複実行しなくてよい．単独実装，または委任契約で要求された場合はexecution担当が最終検証まで行う．

調査量や波及範囲が事前想定を超えた場合，検証を省略して見かけ上完了させない．次を区別して記録する．

- 事前想定と異なった参照集合，設計情報，既存抽象化，テスト支援，環境またはtool上の問題
- 調査によって確定した事実
- 独立して完了できる次の最小単位
- coordination判断が必要な意味論または設計上の選択

残予算が少なくなった時点で，無関係なcleanupや新しいrefactorを停止する．ただし，実装一貫性の確認に必要な読解を機械的に打ち切らない．完了できない場合は，少なくとも現在の実エラー，変更ファイル，想定外を取得して再計画可能な状態を残す．各垂直スライスでcompileを戻し，「最後の一回だけ未実行」という状態を避ける．

**完了条件：** 終了時に，GREENまたは再開可能な実エラーのいずれかを提示できること．

### 6．最終検証

受け入れ基準を満たした後，委任契約でexecution担当へ割り当てられた検証を実行する．単独実装の場合は次をすべて実行する．

1. focused test
2. 原則としてリポジトリ全体の`mvnw.cmd test`または`./mvnw test`
3. 作業状態に応じたdiff check．未コミット変更なら`git diff --check`，commit済みbranch全体なら`git diff --check <base>...HEAD`
4. `git diff`によるscope，stub，TODO，暫定fallbackの確認
5. `git status`による変更ファイルの確認

テスト失敗を既存失敗と判断する場合も，実際のエラーと開始時の状態を比較する．実行できなかった検証は「未実行」と明記し，推定した成功へ置き換えない．

**完了条件：** 受け入れ基準の各項目に対応する実測結果があり，未完了のscope内修正がないこと．

## 完了報告

完了時は次を簡潔に報告する．

```text
実装:
- 変更した振る舞いと主要な実装箇所

検証:
- 実行したコマンド: 実結果

変更ファイル:
- scope内で変更したファイル

設計からの逸脱・残課題:
- なし，または具体的な内容
```

途中終了時は次を必ず含める．

```text
完了済み:
未完了:
実際のcompile/test error:
変更済みファイル:
通過済みテスト:
未実行テスト:
事前想定と異なった点:
調査で確定したこと:
coordination判断が必要な事項:
次の最小checkpoint:
```

「おそらく通る」「残りは簡単」「あと一箇所」のような見込みを，実結果の代わりに使用しない．

## 落とし穴

1. **意図せず調査とtodoだけで終了すること。** 最初のcheckpointをREDまたはcompileへ設定する．想定外の複雑性で到達できない場合は，調査結果と再分割に必要な情報を具体的に残す．
2. **承認済み設計の再設計。** 矛盾がなければ契約どおり実装し，改善案はscope外として分離する．
3. **一括変更による長時間のcompile不能。** 小さい参照集合ごとにcompileを戻す．
4. **既存変更の巻き戻し。** 開始時のstatusとdiffを確認し，自分の変更だけを扱う．
5. **既存テストだけによる意味論の保証。** 設計で重要な不変条件を直接テストする．
6. **検証前のtool call枯渇。** 担当するfocused verificationを優先し，coordination担当の最終検証と重複させない．
7. **未完了状態の曖昧な報告。** 実エラー，変更ファイル，次のcheckpointを具体的に残す．
8. **変更scopeと読解scopeの混同。** 変更ファイルを限定するために，実装一貫性に必要な読解まで省略しない．

## 検証チェックリスト

- [ ] 実装契約，scope，non-goalsの確認
- [ ] 実装コンテキスト目録，追加調査の裁量，既知の不確実性の確認
- [ ] 既存の未コミット変更の把握と保持
- [ ] REDまたは最小compile checkpointの実測
- [ ] 小さい反復ごとのcompileとfocused test
- [ ] フェーズ境界と設計上の不変条件の確認
- [ ] scope内に残る小規模修正の完了
- [ ] 委任契約で割り当てられた検証の実行
- [ ] 単独実装ではfull test，適切なrangeのdiff check，最終statusの確認
- [ ] 実測結果に基づく完了報告または途中報告
