# ZLK Change Coordination

## 概要

ZLKの非自明な変更について，設計，実装単位への分割，委任，統合，完了判定を担当するための手順を定める．サブエージェントの使用自体ではなく，変更全体の整合性と完了に責任を持つ役割に適用する．

このSKILLの目的は，調査だけで終了する委任，コンパイル不能な途中状態，設計上の不変条件違反，検証前のtool call枯渇，仕様の誤読によるリテイクの削減である．

## 適用条件

以下の場合に使用する．

- 複数のコンパイラフェーズまたは複数の実装段階にまたがる変更
- 実装前に設計上の選択や不変条件の整理が必要な変更
- 一つ以上の実装単位を別の担当へ委任する作業
- 途中終了した実装の状態を確認し，残作業を再編成する作業
- 実装結果を統合し，変更全体の完了を判定する作業

次の場合には使用しない．

- 承認済みの限定された変更単位を実装するだけの作業。この場合は`zlk-change-execution`を使用する
- コードを変更しない単純な質問への回答
- 数行の自明な文書修正または機械的修正

## 役割と責任

coordination担当は，変更全体について次の責任を持つ．

- 設計判断と未決事項の区別
- 実装単位間の依存関係と順序の管理
- 各実装担当が単独で一貫した実装を行えるコンテキスト目録の提供
- タスクの不確実性と担当モデルの適性を踏まえた委任可否の判断
- 委任前から存在する作業ツリー変更の保護
- 実diffと実測した検証結果による完了判定
- 小さく明確な残修正の完了，または残作業だけに限定した再委任

委任ツールの`completed`状態，担当者の要約，または「あと一箇所で通る見込み」は完了の証拠としない．

## 手順

### 1．開始状態の固定

最初に以下を確認する．

- 現在のbranchと`git status`
- 既存の未コミット変更と，今回の作業との関係
- 関連する実装，テスト，`AGENTS.md`，`ARCHITECTURE.md`
- 現在再現できる動作，失敗，または不足している言語機能

既存変更を今回の変更と誤認しないよう，委任前の変更ファイル一覧またはdiffを保持する．完了条件は推測ではなく，開始時に観測した状態を基準に定める．

**完了条件：** 既存変更，変更対象，現在の動作を区別して説明できること．

### 2．設計契約の作成

実装前に，少なくとも次を整理する．

1. 目標となる利用者向けまたはコンパイラ内部の振る舞い
2. 関連するコンパイラフェーズと入力IR／出力IR
3. 新しく必要となる情報と，その情報を所有するフェーズまたは型
4. 後続フェーズが利用できる不変条件
5. 再利用すべき既存の抽象化
6. 明示的なnon-goals
7. 受け入れ基準と，それを証明するテスト

あわせて，実装担当が詳細設計や命名を既存コードへ合わせられるよう，次の実装コンテキスト目録を作る．

- 主変更ファイル
- 直接の呼出元と呼出先
- 同種の抽象化，命名，エラー処理の参照例
- 使用するテストクラスとテスト支援API
- 正本となる設計文書
- 変更対象を網羅的に扱うswitch，visitor，printer
- 関連外と判断した主要箇所と，その判断根拠

目録は読解の開始地点でありallowlistではない．実装担当には，実装レベルの一貫性を確認するために必要な追加読解を認める．変更scopeと読解scopeを同一視しない．テストだけの変更でも，受け入れ条件の意味論を確認するためにproduction実装や近接IRの読解が必要になり得る．

選択肢がある場合は，既存テストを温存するためだけの例外的な内部表現より，意味論に基づく一貫した規則と後続フェーズで利用できる不変条件を優先する．現在の構造の説明は`ARCHITECTURE.md`を正本とし，作業手順を同文書へ混在させない．

**完了条件：** 実装担当が設計を再考せず，決定済み事項と未決事項を区別できること．

### 3．実装単位への分割

大きな変更を一件の委任へまとめない．次のいずれかで分割する．

- 一つの観測可能な振る舞いを端から端まで通す垂直スライス
- 明確な入力，出力，不変条件を持つフェーズ境界
- 独立してREDからGREENまで検証できる不具合または機能

各単位には，最初の実装checkpointを置く．不具合修正や振る舞い追加では，目的を持って関連実装とテストを読んだ後の「失敗テスト追加とRED確認」を原則とする．基盤変更では，最小のproduction compileまたはfocused testまでを早期checkpointとする．

変更構造だけでなく，調査量の不確実性も分割判断へ含める．主要なcall site数，類似抽象化，sealed hierarchyやvisitorへの波及，テスト支援APIによる観測可能性，複数フェーズへの波及が不明な場合は，coordination担当が先に目録を補うか，成果物を明示したreconnaissanceを分離するか，実装単位をさらに縮小する．不確実性を実装担当の自己管理だけに委ねない．

調査とtodo作成だけで終了し得る大きさは避ける．複数単位が同じファイルを変更する場合は，並列委任より順次委任を優先する．

次の場合は，委任promptを詳細化するよりcoordination担当が直接実装する判断を優先する．

- 実装中も一貫した設計判断が必要で，契約だけでは選択肢を閉じられない変更
- 同一ファイル内の密結合したrefactor
- 失敗時の復旧に作業ツリー全体の理解が必要な変更
- 利用可能な担当モデルでは詳細設計を維持できないと判断できる変更
- 委任，独立検証，修復の総コストが直接実装を上回る変更

**完了条件：** 各単位に独立したscope，最初のcheckpoint，GREEN条件があること．

### 4．実装契約の委任

委任promptには，親会話を参照しなくても作業できるよう，次を明記する．

```text
目標:
現在の動作または再現手順:
承認済み設計:
実装コンテキスト目録:
追加調査の裁量:
既知の不確実性:
変更範囲:
対象外事項:
受け入れ基準:
最初の実装checkpoint:
必須テストと検証コマンド:
保持すべき既存変更:
Git操作および再委任の禁止事項:
完了報告の形式:
```

実装担当には`zlk-change-execution`の使用を求める．曖昧な設計判断を委任先へ暗黙に押し付けない．必要な情報がリポジトリ内にある場合は，正確なファイルまたは型を示す．

目録は追加調査を禁止する境界として使わない．詳細設計，命名，既存抽象化，呼出関係，テスト慣例の一貫性に必要な追加読解を認め，目的や仮説を持たないリポジトリ全体の網羅探索だけを避けるよう伝える．

検証責任を委任promptで分担する．coordination担当が存在する場合，execution担当の既定責任はproduction compile，変更に最も近いfocused test，自身のscope diffの確認とする．統合後のfocused test，full test，baseを考慮したdiff check，最終statusはcoordination担当が直接行う．単独実装ではexecution担当が最終検証まで担う．タスクと検証責任が利用可能な予算に収まるよう分割すること自体をcoordination担当の責任とし，実装担当へ抽象的に「tool callを残す」と要求するだけで済ませない．

内部表現にnegative requirementがある場合，「二重管理を避ける」のような目的だけでなく，禁止する具体的な型／key／fallbackと，必須となる代替構造を委任契約へ記載する．可能なら完了時に検索またはdiffで確認できる条件へ変換する．

**完了条件：** 委任promptだけで，実装範囲とGREEN条件を一意に判断できること．

### 5．途中終了の処理

実装担当が未完了で終了した場合は，自己申告だけで状態を判断しない．coordination担当が次を直接取得する．

- 実際の変更ファイルとdiff
- production compileまたはfocused testの実エラー
- 通過済み，失敗，未実行のテスト
- 設計契約に対して完了した項目と残った項目
- 事前想定と異なった参照集合，設計情報，既存抽象化，テスト支援，環境またはtool上の問題
- 既に確定したこと，独立して完了できる最小単位，coordination判断が必要な事項

意図せず調査だけで終了した場合も，まず委任時の想定と実際の差分を特定する．同じpromptを小さく言い換えて再送せず，コンテキスト目録，設計契約，タスク境界，担当モデルの適性のどれを見直すべきか判断する．調査で判明した事実が再計画に必要なら成果として利用するが，実装完了とは扱わない．コンパイル不能な変更がある場合は，既に完了した調査を繰り返させず，実エラー，保持すべき変更，最初の再compile checkpointを継続担当へ渡す．

残修正が数行程度で，設計も修正箇所も明確なら，coordination担当が直接完了させる．それ以外は，残作業だけを新しい実装契約にする．

**完了条件：** 次の担当が推測せず，観測済みのエラーと残作業から開始できること．

### 6．統合と独立検証

実装担当の報告後，coordination担当が以下を直接行う．

1. 委任前後のdiffによる，変更の存在と既存変更保持の確認
2. 実際の変更ファイルと委任scopeの一致確認
3. TODO，stub，silent fallback，暫定的なfail-fastの検索
4. focused testの再実行
5. 原則としてfull testの再実行
6. 作業状態に応じたdiff checkと最終`git status`
7. 設計契約，フェーズ境界，不変条件への適合性レビュー

未コミット変更を検査する場合は`git diff --check`を使う．PR前など，変更が既にcommitされている場合は`git diff --check <base>...HEAD`のようにbaseとのrangeを明示する．通常の`git diff --check`を，branch全体の検査証拠として扱わない．

compileと既存テストがGREENでも，表現のkind，rank，循環，重複保持など，今回の設計で定めた不変条件がテストで十分に表現されていない場合がある．その場合は，不変条件を直接確認するテストまたはコードレビューを追加する．独立したdiffレビューが必要なら，既存の`independent-diff-review`を利用する．

テストを実行できない場合は，理由と未検証範囲を明記し，GREENとして報告しない．

**完了条件：** 受け入れ基準の各項目を，diff，テスト結果，または明示的なレビュー結果へ対応付けられること．

## 完了報告

次を簡潔に報告する．

- 実装された振る舞いと主要な設計判断
- 変更された主要ファイル
- 実行したfocused testとfull test，および実結果
- 実行したdiff checkの対象rangeと最終status
- 未検証事項または残課題。存在しない場合は，未完了を示唆する文言を残さない

## 落とし穴

1. **一件の委任が大きすぎること。** 調査ではなくGREENまで到達できる垂直スライスへ縮小する．
2. **担当者の完了報告への依存。** 実diffと実測したテストをcoordination担当が確認する．
3. **既存テストが通ることだけによる完了判定。** 設計上の不変条件と新しい受け入れテストも確認する．
4. **途中状態への同一promptの再送。** 実エラーを取得し，残作業だけの継続契約を作る．
5. **検証前のtool call枯渇。** 各スライスで早期にcompileを戻し，最後の検証予算を先に確保する．
6. **仕様を読まずに制限と判断すること。** 既存の構文，テスト，意味論を確認し，正しい利用例でE2Eテストを作る．
7. **変更scopeと読解scopeの混同。** 変更ファイルを限定するために，実装一貫性に必要な読解まで禁止しない．
8. **不確実性の実装担当への転嫁。** 調査量を把握できないまま固定scopeを渡し，途中終了後も同じ契約を再送しない．
